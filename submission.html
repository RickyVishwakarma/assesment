Running it

From clone to your own document, in five steps

The rules approach needs nothing but Python. Each additional approach adds one dependency, and any that is missing disables only itself.

  1. Clone and install

    # torch first — the CUDA build depends on your hardware
git clone https://github.com/RickyVishwakarma/assesment.git
cd assesment
git lfs pull

pip install torch --index-url https://download.pytorch.org/whl/cu128  # or: pip install torch
pip install -r requirements.txt
python -m spacy download en_core_web_sm

    git lfs pull fetches the 500 MB of DistilBERT weights. Skip it and every approach except the small model still works — or rebuild the weights locally in about 13 minutes with python -m docintel train --what all.

  2. Check what your machine can run

    python -m docintel doctor

    Reports torch, CUDA, spaCy, Ollama and every artefact. If the weights are unfetched LFS pointers it says so directly rather than failing later with a deserialisation error.

  3. Run one document through all four approaches

    python -m docintel extract \
    --file data/corpus/pdfs/demo-0000-referral_letter-t11.pdf \
    --approach all

    The repository ships 1,300 PDFs. The ten named demo-* are the ones to look at first — held-out templates, never trained on and not part of the gold set, one per document type.

    data/corpus/pdfs/
      demo-*       10 · never seen by any stage
      gold_synth-*  90 · the human-verified test set
      train-*     1000 · silver-labelled
      val-*       200

    demo-0004-remittance_advice-t11.pdf is the interesting one: it carries a service-line table, which is where the rules engine scores 0.000 and the LLMs do not.

  4. Try your own PDF

    python -m docintel extract --file /path/to/your-document.pdf --approach all

    Any PDF works, digital or scanned — scanned pages route through OCR automatically. One caveat worth knowing before you see it: on a document from outside the healthcare domain the rules engine answers confidently and wrongly, because its confidence scores reflect which rule fired rather than whether the answer is right. Fed the assignment brief itself, it returned amount_paid = 4 and total_charge = 20 — section numbers read as currency — while the LLM returned nothing at all. That gap is discussed in §5.

  5. Reproduce every number on this page

    python scripts/demo_unseen.py                    # 10 unseen docs, scored
python -m docintel evaluate --split gold_synth --approach all
python scripts/error_analysis.py --split gold_synth
python -m pytest tests/ -q                       # 109 tests

    On a machine with under 8 GB of RAM, run --approach nlp small_model llm_frontier first and then --approach llm_local --merge — torch and Ollama cannot both be resident here.

Or serve it over HTTP

python -m uvicorn docintel.api:app --port 8000

curl.exe -F "file=@data/corpus/pdfs/demo-0000-referral_letter-t11.pdf" \
     "http://127.0.0.1:8000/extract?approach=all"

GET /health lists which approaches loaded. On Windows use curl.exe, not curl — PowerShell aliases the latter to Invoke-WebRequest, which has no -F flag.

Requirement 1 · Training data

Where the documents come from, and why the test set can be trusted

There is no public corpus of labelled healthcare faxes, and real ones are PHI. So the corpus is generated. That creates one serious risk — a model memorising the generator — and two controls defuse it.

1,300 documents across six types: referral letters, prior-authorisation requests, lab orders, CMS-1500 claims, remittance advices and intake forms. Real ICD-10 and CPT codes. NPIs carry a valid Luhn check digit, and each page also carries a decoy 10-digit number that fails it.

Control one: template hold-out. Templates 1–10 are used for training, 11–14 only for testing — different geometry, different label wording. Control two: real OCR damage. Half the corpus is rasterised at 200 dpi, skewed, blurred, speckled, JPEG-compressed, and read back through an OCR engine.

The ceiling every approach sits under

Only 85.3% of gold values survive OCR on the scanned half — 98.9% on the clean half. The rest were destroyed before any extractor ran. Every scanned-condition number should be read against 85.3%, not against 100%.

Silver labels, and a teacher that was scored

The small model trains on labels the local 3B produced, never on generator truth. Because the generator does know the truth, the teacher can be scored — which most silver pipelines skip.

Those 625 whitespace-tolerant matches are about 5% of the training signal — values the layout broke across a line, which a plain text.find() would have discarded.

The teacher’s worst field is not noisy, it is biased: 106 of 110 document_date errors take the Printed: footer instead of the document date. Random teacher noise averages away in the student. Systematic bias is learned.
Requirement 2 · The three systems

Three approaches, built four ways

The brief asks for three. There are four because this machine has 7.4 GB of RAM, which caps a local model at about 3B — and a 3B model is arguably itself a small model. Using it as the general-LLM baseline alone would have made the central question unanswerable.

Rules / NLPLabel anchors plus spatial lookup over OCR word boxes. Regex and checksums validate candidates rather than find them. TF-IDF into LinearSVC for doc type.
Small modelDistilBERT-cased 66M, token classification over 31 BIO tags, plus a second head for doc type. Extractive, so it cannot return a value absent from the page.
Local LLMQwen2.5-3B-Instruct via Ollama, schema-constrained JSON, temperature 0. Offline and free — the baseline anyone can reproduce.
Frontier LLMCached reference tier. Cost estimated from published per-token pricing on measured token counts, never metered, and labelled as such in every table.

All four implement one interface, extract(OcrDocument) → ExtractionResult, so the CLI, API and evaluator cannot treat one specially. One normalize.py decides that 03/14/2025, 14-Mar-2025 and 2025-03-14 are the same date, and the scorer imports the same module the approaches do. If each approach normalised its own output, whichever happened to match the scorer’s preferred format would gain an advantage unrelated to extraction quality.

Relationships: the service-line task

Claims and remittance advices carry a table of service lines — repeating rows of {procedure, date, units, charge, paid}. One correct row means five correct values kept together. 30 of the 90 gold documents carry them, 84 rows in total, scored as set-F1 over normalised tuples.

Why rules score exactly zero and cannot be tuned off it

The approach finds a label and reads the value beside it. A service-line table has one header for N rows, so there is nothing to match per row and no way to express “these five values belong together” in a dictionary of label variants. The small model fails for a related reason: BIO tagging marks which tokens are a charge, but carries no representation of which row a charge belongs to. Row grouping needs 2-D layout encoding — LayoutLM and relatives — or a decoder that emits structured output directly.

The conclusion is about the corpus, not about multilingual extraction: this corpus does not test multilingual robustness.

Determinism

The 1.00 that did not survive 90 documents

All four approaches produce byte-identical output across 3 runs on 5 documents. But three full 90-document passes of the local LLM scored 0.835, 0.841 and 0.842, with hallucination moving between 0.005 and 0.007. That spread of 0.007 is wider than its entire measured lead over the rules engine. Rules and the tagger are deterministic by construction; the LLM’s 1.00 on five documents means divergence is rare, not absent.

Requirement 5 · The engineering question

The smallest adequate system, and where an LLM still earns its cost

Rules are the cheapest adequate system for flat field extraction — 86% of frontier F1 at 6 MB and 11 ms. For structured repeating content they do not compete, and no amount of rule-writing changes that.

The comparison that should decide the architecture is rules against the local 3B, because that is the choice a team without an API budget actually faces.

That 0.017 sits inside the bootstrap confidence intervals, so on flat fields the two are statistically indistinguishable. The margin is also unstable in two ways. It moved during the project: before gold verification, rules were ahead by 0.002. And it moves between runs: three passes of the local LLM scored 0.835, 0.841 and 0.842. When two systems trade places depending on how 21 of 923 fields are adjudicated, and one of them will not return the same score twice, accuracy is not the dimension that should decide the architecture. The latency gap, the determinism and the inability to hallucinate are not close, and they do not move.

Where a general LLM earns its cost

  • Structured repeating content. Service lines: 0.000 against 0.917. The only task here where the non-LLM approaches do not merely score lower — they do not work.
  • Roles for values that look identical. The small model returns document_date’s value for date_of_service in 11 of 60 cases. The LLM scores 0.723 against the tagger’s 0.460.
  • Documents with no anchors. 73 of the rules engine’s 77 misses are on prose layouts, where the value sits inside a sentence with no Label: to key on.
  • Unanticipated layouts and wording. The dictionary does not know five label variants that occur only on held-out templates.
  • Knowing when to return nothing. Given a document from outside the domain, the rules engine returned amount_paid = 4 and total_charge = 20 — section numbers read as currency — while the LLM returned nothing for all 15 fields.

What I would build

The caveat this design depends on

The confidence scores are not calibrated. A real blank CMS-1500 from cms.gov produced patient_name = "Self Spouse Child Other" at confidence 0.90–1.05. Those numbers reflect which rule fired, not whether the answer is right. Routing needs abstention first: require a label anchor within a bounded distance, type-validate the value, and reject fields whose document-type prior does not match.

What I would do next, in order

  • Fix the two rare fields. About 160 training spans each, −0.490 mean F1 against the teacher. Class-balanced sampling, not a bigger model.
  • Improve capture before improving models. The 85.3% OCR ceiling caps everything and better scanning helps all four approaches at once.
  • Add abstention and calibrate confidence. The routing design does not work without it.
  • Fix the teacher’s Printed: bias with one prompt instruction; the student inherits the improvement.
  • Then revisit the small model, which the curve says is still data-limited.

Three leaks found and closed

Each would have flattered a result. All three are now guarded by tests/test_no_leakage.py.

  • The rules approach imported the generator’s own label dictionary (from ..gen.render import LABELS), giving it foreknowledge of wording that appears only on held-out templates. It now builds its vocabulary from training documents alone. The five label variants it consequently does not know are a finding about dictionary brittleness, not a defect to patch.
  • The evaluator stamped every gold record human_verified whether or not anyone had reviewed it, because it keyed on presence in the file rather than each record’s own flag.
  • OCR assembly collapsed two-column rows to a single space, making Patient Name: beside Reference #: indistinguishable from prose and merging adjacent columns into one field.

Known limitations

  • The corpus is synthetic. Real documents have handwriting, stamps and multi-page threading this generator does not produce, so absolute numbers would drop on them. What holds is the relative comparison: identical documents, held-out layouts, real OCR damage.
  • No real documents in the test set. The plan included a slice of public forms; I could not source filled, labelable healthcare documents in the time available. This is the biggest gap in the submission.
  • The frontier tier is not independently reproducible. It is a cached reference point and its cost is estimated, not metered.
  • The error taxonomy is rule-assigned. Some OCR whitespace damage is coded FORMAT_NORMALISATION when it belongs in OCR_CORRUPTION, so 51 is a floor on OCR’s share, not a full accounting.
