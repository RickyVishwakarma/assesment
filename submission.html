Requirement 1 · Training data

Where the documents come from, and why you can trust the test set

No public corpus of labelled healthcare faxes exists, and real ones are PHI. So the corpus is generated — which creates exactly one serious risk, and the design is built around defusing it.

1,300 documents across six types: referral letters, prior-authorisation requests, lab orders, CMS-1500 claims, remittance advices and intake forms. Real ICD-10 and CPT codes; NPIs that pass the Luhn check digit, alongside a decoy 10-digit number that fails it.

Half the corpus goes through real OCR damage

Rasterised at 200 dpi, then skewed, blurred, speckled, JPEG-compressed and in some cases fax-thresholded to 1-bit, and read back through an OCR engine. That noise isn't simulated.

The ceiling every approach sits under

Only 85.3% of gold values survive OCR on the scanned half (430 of 435, or 98.9%, on the clean half). The rest were destroyed before any extractor ran. Read every scanned-condition number against 85.3%, not against 100%.

Silver labels, and a teacher that got scored

The small model trains on labels the local 3B produced — never on generator truth. That's what the assignment asks to demonstrate, and it's what you'd actually have in production. Because the generator does know the truth, the teacher can be scored, which most silver pipelines never bother to do.

Getting from a returned value to a trainable character span is the unglamorous step that decides how much supervision survives: 11,914 spans matched exactly, 625 needed whitespace tolerance, 66 needed punctuation-insensitivity, 20 fuzzy, and 165 were unalignable and dropped. Those 625 are about 5% of the training signal — values the layout broke across a line, which a plain text.find() would have thrown away.

The teacher’s worst field isn’t noisy, it’s biased: 106 of 110 document_date errors are the model taking the Printed: footer instead of the document date. Random teacher noise gets averaged away by the student. Systematic bias gets learned.
Requirement 2 · The three systems

Three approaches, built four ways

The assignment asks for three. There are four, because with 7.4 GB of RAM the biggest local model is ~3B — and a 3B model is arguably itself a “small model”. Calling it the general LLM would have made the central question unanswerable.

Rules / NLPLabel anchors + spatial lookup over OCR boxes. Regex and checksums validate candidates rather than find them. TF-IDF → LinearSVC for doc type.
Small modelDistilBERT-cased 66M, token classification over 31 BIO tags, plus a second head for doc type. Extractive — structurally cannot hallucinate.
Local LLMQwen2.5-3B-Instruct via Ollama, schema-constrained JSON, temperature 0. Fully offline and free — the reproducible baseline.
Frontier LLMCached reference tier. Cost estimated from published per-token pricing, never metered, and labelled that way in every table.

All four implement one interface — extract(OcrDocument) → ExtractionResult — so the CLI, the API and the evaluator cannot accidentally treat one specially. A single normalize.py decides that 03/14/2025, 14-Mar-2025 and 2025-03-14 are the same date, and the scorer imports the same module the approaches do. If each normalised its own output, whichever happened to match the scorer's preferred format would win for a reason unrelated to extraction quality.

Relationships: the service-line task

Flat fields are only half the brief. Claims and remittance advices carry a table of service lines — repeating rows of {procedure, date, units, charge, paid} — where getting one right means getting five values right and keeping them on the same row. 30 of the 90 gold documents carry them; 84 rows in total, scored as set-F1 over normalised tuples.

 The widest margin anywhere in the project, and a difference in kind rather than degree. Note the local model’s asymmetry — recall 0.905 against precision 0.571: it finds nearly every real row and invents 57 extra ones.
Why rules score exactly zero, and can’t be tuned off it

The whole approach keys on finding a label and reading the value beside it. A service-line table has one header for N rows, so there is nothing to match per row and no way to express “these five values belong together” in a dictionary of label variants. The small model fails for a related reason: BIO tagging marks which tokens are a charge, with no representation of which row a charge belongs to. Row grouping needs 2-D layout encoding (LayoutLM and relatives) or a decoder that emits structured output.

Spanish is not a weak slice, and that’s a finding about the corpus rather than about multilingual extraction. I built 13% Spanish documents expecting to report a penalty. The honest conclusion is that this corpus doesn’t test multilingual robustness.

Determinism, measured rather than asserted

The 1.00 that didn’t survive contact with 90 documents

All four approaches produce byte-identical output across 3 runs on 5 documents. But three full 90-document passes of the local LLM scored 0.835, 0.841 and 0.842, with hallucination moving between 0.005 and 0.007. The spread — 0.007 — is wider than its entire measured lead over the rules engine. Rules and the tagger are deterministic by construction; the LLM’s 1.00 on five documents means divergence is rare, not absent.

How much silver data does the small model actually need?

100 documents is unusable — not enough signal to learn 31 BIO tags. 300 is the elbow, giving 80% of the final F1 for 30% of the labelling. And it is still climbing at 1,000 (+0.061 on the last step), so the small model is data-limited rather than architecture-limited — but the teacher is only 86.0% accurate, so the curve will flatten near that ceiling regardless of volume. Past this point the higher-leverage move is a better teacher, not more documents from the same one.

1,000 is the whole silver set, so the last point is the shipped model — which is why it reproduces 0.782 exactly rather than merely approaching it. The dashed line is the rules engine, which the small model never reaches.

Requirement 5 · The engineering question

The smallest adequate system, and where an LLM still earns its cost

Rules are the cheapest adequate system for flat field extraction — 86% of frontier F1 at 6 MB and 11 ms. For structured repeating content they don’t compete, and no amount of rule-writing changes that.

The comparison that should actually decide the architecture is rules against the local 3B, because that’s the choice a team without an API budget really faces:

RulesLocal LLM 3B
F10.8250.842LLM ahead by +0.017

Service lines0.0000.701the one place it wins outright

That +0.017 sits inside the bootstrap confidence intervals, so on this corpus the two are statistically indistinguishable on flat fields. And the margin is unstable in two separate ways: it moved during the project — before gold verification rules were ahead by 0.002 — and it moves between runs, since three passes of the local LLM scored 0.835, 0.841 and 0.842. When two systems trade places depending on how you adjudicate 21 of 923 fields, and one of them won’t return the same score twice, the accuracy difference isn’t what should decide the architecture. The latency gap, the determinism and the inability to hallucinate are not close, and they don’t move.

Where a general LLM genuinely earns its cost

  • Structured repeating content. Service lines: 0.000 → 0.917. The only task here where the non-LLM approaches don’t merely score lower, they don’t work at all.
  • Roles for values that look identical. The small model returns document_date’s value for date_of_service in 11 of 60 cases; the LLM scores 0.723 against the tagger’s 0.460.
  • Documents with no anchors. 73 of the rules engine’s 77 misses are on prose layouts, where the value sits inside a sentence with no Label: to key on. Rules don’t degrade there — they fail outright.
  • Layouts and wording nobody anticipated. The dictionary genuinely doesn’t know five label variants that occur only on held-out templates. A dictionary knows what it was told; an LLM doesn’t need telling.

The caveat that makes this design honest

The confidence scores aren’t calibrated. I ran a real blank CMS-1500 from cms.gov through the rules engine and got patient_name = "Self Spouse Child Other" at confidence 0.90–1.05. Those numbers reflect which rule fired, not whether the answer is right. Routing needs abstention first: require a label anchor within a bounded distance, type-validate the value, and reject fields whose document-type prior doesn’t match.

What I’d do next, in order

  • Fix the two rare fields. ~160 training spans each and −0.490 mean F1 against the teacher — class-balanced sampling, not a bigger model.
  • Improve capture before improving models. The 85.3% OCR ceiling caps everything, and better scanning helps all four approaches at once.
  • Add abstention and calibrate confidence. The routing design above doesn’t work without it.
  • Fix the teacher’s Printed: bias with one prompt instruction — the student inherits the improvement.
  • Then revisit the small model, which the curve says is still data-limited.

Three leaks found and closed

Each would have quietly flattered a result. They’re listed because a comparison is only as trustworthy as its worst unexamined assumption — and all three are now guarded by tests/test_no_leakage.py.

  • The rules approach imported the generator’s own label dictionary (from ..gen.render import LABELS), handing it perfect foreknowledge of wording that appears only on held-out templates. It now builds its vocabulary from training documents alone — and the five label variants it consequently doesn’t know are a real finding about dictionary brittleness, not a defect to patch.
  • The evaluator stamped every gold record human_verified whether or not anyone had looked at it, because it keyed on presence in the file rather than each record’s own flag.
  • OCR assembly collapsed two-column rows to a single space, making Patient Name: beside Reference #: indistinguishable from prose and merging adjacent columns’ values into one field.

Known limitations

  • The corpus is synthetic. Real documents have handwriting, stamps and multi-page threading this generator doesn’t produce, so absolute numbers would drop on them. What holds is the relative comparison: identical documents, held-out layouts, real OCR damage.
  • No real documents in the test set. The plan included a slice of public forms; I couldn’t source filled, labelable healthcare documents in the time available. This is the single biggest gap in the submission.
  • The frontier tier isn’t independently reproducible. It’s a cached reference point and its cost is estimated, not metered.
  • The error taxonomy is rule-assigned. Some OCR whitespace damage lands in FORMAT_NORMALISATION when it belongs in OCR_CORRUPTION, so 51 is a floor on OCR’s share, not a full accounting.
